# MemGraphRAG Enhanced: 論文からのクリーンルーム再実装と独自拡張による高精度マルチホップ質問応答

**原論文のアルゴリズム記述のみからクリーンルーム実装 → 6 つの独自拡張と LadybugDB グラフバックエンドで HotpotQA 87.6% を達成**

---

## 概要

本稿では、MemGraphRAG (Hu et al., 2025) の**クリーンルーム再実装**とその体系的拡張を報告する。原論文のアルゴリズム記述のみを入力とし、オリジナルのソースコードを参照せずに TypeScript でシステム全体を設計・実装した。このクリーンルーム過程で、論文に明記されていない暗黙的な設計判断を複数特定し、それらを改善の起点として 6 つの独自拡張を導入した: (1) 選択的ハブ抑制付き 4 層異種グラフ、(2) 質問タイプ別の検索・プロンプト戦略、(3) 推論モデルの深度制御を活用した回答生成、(4) 専門用語辞書・シソーラスによるクエリ拡張、(5) 言語学的正規化に基づく堅牢な評価関数、(6) LadybugDB グラフバックエンドとインメモリキャッシュアダプター。クリーンルームベースライン単体で 55.8% を達成した後、各拡張を段階的に適用し、SQLite ストレージで **83.6%**、さらに LadybugDB グラフバックエンドへの移行により HotpotQA 500 問で **String Accuracy 87.6%** を達成した。原論文の 71.6% から **+16.0pt の改善**、クエリ速度 2.7s/query（非キャッシュ比 18.5 倍高速化）である。

---

## 1. はじめに

知識グラフ構造と密ベクトル検索を組み合わせた Retrieval-Augmented Generation（RAG）システムは、マルチホップ質問応答の有力なアプローチとして注目されている。MemGraphRAG (Hu et al., 2025) は、ベクトルストアとグラフストアの二重記憶構造に Personalized PageRank（PPR）を組み合わせたメモリ中心アーキテクチャを提案し、HotpotQA の distractor 設定 500 問サブセットで 71.6% の String Accuracy を報告した。

我々はこのシステムの**クリーンルーム再実装**に着手した — 論文に記述されたアルゴリズムのみから、オリジナルのソースコードを参照せずに全体を実装する手法である。この手法は 2 つの目的を持つ: (a) 独立した再現により論文のアーキテクチャ上の主張を検証すること、(b) 暗黙的な設計判断や未規定のコンポーネントを特定し、改善の余地を発見すること。

クリーンルーム過程で、論文がアルゴリズム的には完全でありながら、いくつかの重要なエンジニアリング上の判断を暗黙に残していることが判明した:

1. **グラフトポロジーの扱い** — 論文は fact–passage グラフを記述するが、高次数のオントロジーノードが PPR スコア分布に与える影響を規定していない。我々の分析で、均一な扱いではスキーマハブがスコア吸収源となることを発見した。
2. **質問タイプの異質性** — 論文は単一のクエリパイプラインを使用するが、bridge 質問と comparison 質問は本質的に異なる検索戦略を必要とする。
3. **LLM 生成パラメータ** — 論文執筆後に利用可能となった推論モデル（GPT-5 系、o 系）の推論深度制御（`reasoning_effort`、`verbosity`）が考慮されていない。
4. **語彙資源** — 検索時のエンティティ一致を改善できるドメイン固有の専門用語や同義語関係が活用されていない。

我々のクリーンルームベースラインは 55.8% の String Accuracy を達成した — 論文の 71.6% を下回るが、これはコーパスの違いや未規定のハイパーパラメータ選択に起因すると考えられる。上記 4 領域への体系的拡張により精度を段階的に引き上げ、SQLite バックエンドで 83.6% を達成し原論文を +12.0pt 上回った。さらに LadybugDB グラフバックエンドとインメモリキャッシュアダプターへの移行により 87.6%（+16.0pt）を達成し、クエリ速度も 2.7s/query に高速化された。

本稿では、クリーンルーム設計の過程と 5 つの拡張の両方を報告し、14 回のベンチマーク反復を通じて得られた知見を議論する。

## 2. 論文からのクリーンルーム設計

### 2.1 設計方法論

本実装は厳密なクリーンルーム規律に従った: 唯一の入力は公開論文 (Hu et al., 2025, arXiv:2606.00601v1) とそのアルゴリズム記述である。著者のソースコード、事前学習モデル、データセットは一切使用していない。実装は仕様駆動開発（SDD）ワークフローで進行した:

1. **要件分析** — 論文のアルゴリズム記述、アーキテクチャ図、評価プロトコルから 69 件の EARS 形式要件を抽出。
2. **設計仕様** — 要件を 4 層アーキテクチャ（Domain / Application / Infrastructure / Interface）にマッピングする 69 件の設計仕様を作成。
3. **タスク分解** — 8 フェーズ・77 タスクに分解し、レビュー承認後に着手。
4. **テストファースト実装** — 各コンポーネントを Red→Green→Blue の TDD サイクルで構築し、354 件のユニットテストを作成。

### 2.2 論文アーキテクチャの忠実な再現

クリーンルーム実装は論文のコアアルゴリズムを忠実に再現している:

**4 段階インデキシングパイプライン (Algorithm 1):**

| ステージ | 論文の記述 | 本実装 |
|---------|-----------|--------|
| Stage I | 文書チャンキングとファクト抽出 | Markdown 見出しベースのチャンカー + 二重抽出（NLP + LLM） |
| Stage II | 頻度安定化を伴うスキーマ正規化 | SymbolicCanonicalizer（昇格閾値 ≥ 2） |
| Stage III | LLM ベースの矛盾検出と解決 | SymbolicConflictDetector + LLMConflictResolver |
| Stage IV | グラフ射影とベクトル埋め込み | SQLite グラフストア + OpenAI 埋め込みインデックス |

**PPR ベースクエリパイプライン:**

| コンポーネント | 論文の記述 | 本実装 |
|-------------|-----------|--------|
| ベクトル検索 | クエリ埋め込み、top-K ファクト/パッセージ取得 | VectorMemoryFilter（コサイン類似度） |
| ノード初期化 | 検索スコアから PPR シード | SimpleNodeInitializer（fact/passage/schema シード） |
| PPR | テレポーテーション付きべき乗反復 | SimplePPR（α, ε, 最大反復数を設定可能） |
| コンテキスト構築 | パッセージランキング、LLM プロンプト構築 | ContextBuilder（トークン制限付きパッセージ組立） |
| LLM 生成 | コンテキストから回答生成 | OpenAILLMProvider（構造化プロンプティング） |

### 2.3 論文に規定されていない設計判断

クリーンルーム過程で、論文がアルゴリズム的に完全でありながら、エンジニアリング上の判断を暗黙に残している領域を複数特定した。これらが拡張の出発点となった:

| 未規定領域 | クリーンルームでの判断 | 拡張（§3） |
|-----------|---------------------|-----------|
| 高次数ノードの PPR 処理 | 当初は均一処理（論文忠実） | §3.1 選択的ハブ抑制 |
| bridge vs. comparison の処理 | 当初は単一パイプライン | §3.2 質問タイプ別ルーティング |
| LLM 生成パラメータ | 当初は temperature のみ | §3.3 推論深度制御 |
| 語彙的正規化 | 当初はなし | §3.4 ドメイン語彙統合 |
| 回答評価指標 | 当初は単純部分文字列一致 | §3.5 堅牢な評価フレームワーク |

### 2.4 クリーンルームベースラインの結果

論文忠実な再現は HotpotQA 500 問で **String Accuracy 55.8%** を達成した（v1）。論文の 71.6% を下回るが、以下の要因に起因すると考えられる:

1. **コーパスの違い** — 本コーパス（MarkItDown で変換した学術論文 100 本）は論文の Wikipedia ベース知識源と異なり、ドメインシフトが生じる。
2. **埋め込みモデルの違い** — 本実装は text-embedding-3-small を使用; 論文の埋め込みモデルは未規定。
3. **ハイパーパラメータ感度** — チャンクサイズ、PPR テレポート確率、コンテキストトークン制限など、論文に規定されていないパラメータの調整が必要。
4. **未規定領域での実装の相違** — 上記の設計判断は不可避的に原著者の選択と異なる。

初期のギャップにもかかわらず、クリーンルームベースラインは論文のコアアーキテクチャ上の主張を検証した: PPR ベースのパッセージランキングを伴う二重ストア設計はナイーブなベクトルのみの RAG を上回り、スキーマ正規化パイプラインは抽出された関係を正常に正規化する。

## 3. 独自の拡張

忠実なクリーンルーム基盤の上に、再現過程で特定した未規定領域を対象として 5 つの拡張を導入した。各拡張は独立して開発・ベンチマークされ、測定可能な改善を実証した後にのみ統合された。

### 3.1 全体構成

```
┌──────────────────────────────────────────────────────────────┐
│            インデキシングパイプライン（論文忠実）               │
│                                                              │
│  文書 → Markdown チャンキング → 二重抽出 (NLP + LLM)          │
│    → スキーマ正規化 → 矛盾解決 → グラフ射影 → ベクトル索引     │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│            クエリパイプライン（論文 + 独自拡張）                │
│                                                              │
│  質問 → [拡張] 辞書照合 → [拡張] シソーラス拡張               │
│    → ベクトル検索 → [拡張] 質問タイプ別ノード初期化            │
│    → [拡張] ハブ抑制付き PPR → コンテキスト構築                │
│    → [拡張] 推論深度制御付き LLM 生成                         │
└──────────────────────────────────────────────────────────────┘

[拡張] = 論文の仕様を超える独自拡張
```

### 3.2 4 層異種グラフ

論文は fact–passage の二部グラフを記述しているが、本実装ではこれを **4 層の異種グラフ** に拡張し、PPR でより豊かなスコア伝播を可能にした:

| 層 | ノードタイプ | 説明 | 例 |
|----|-------------|------|-----|
| **オントロジー層** | `schema:` | 正規化された関係型（headType, relation, tailType） | `(Person, born_in, City)` |
| **ファクト層** | `fact:` | スキーマに紐づく具体的な関係インスタンス | `(Albert Einstein, born_in, Ulm)` |
| **パッセージ層** | `passage:` | 出典メタデータ付きのソーステキストチャンク | Wikipedia 記事の一節 |
| **エンティティ層** | `entity:` | NLP および LLM により抽出された固有表現 | `Albert Einstein` |

**エッジタイプ** はこれらの層を横断的に接続する:

- `schema_instance`: スキーマ → ファクト（型所属）
- `fact_evidence`: ファクト → パッセージ（出典リンク）
- `entity_cooccurrence`: エンティティ ↔ エンティティ（パッセージ内共起）
- `entity_mention`: エンティティ → パッセージ（接地）

この階層設計により、PPR アルゴリズムはクエリに一致するファクトからスキーマ型を経由してエビデンスとなるパッセージへと、意味的階層を横断してスコアを伝播できる。

### 3.3 インデキシングパイプライン

**Stage I — 抽出。** 文書は Unicode 正規化の後、Markdown 見出しベースのチャンカーでセクション単位に分割される。各チャンクは二重抽出パスで処理される:

- **NLP 抽出器**: ルールベースの固有表現認識
- **LLM 抽出エージェント**: LLM に JSON 形式で `{entities, relations}` の構造化抽出を指示し、エンティティ型と信頼度スコアを含む出力を得る

**Stage II — スキーマ正規化。** 抽出された関係トリプルは正規スキーマに正規化される。頻度ベースの安定化機構により、複数文書にわたって出現するスキーマ（閾値 ≥ 2）が昇格し、関連ファクトがクエリ時に活性化される。

**Stage III — 矛盾解決。** 矛盾するファクト（例: 同一エンティティに対する異なる生年月日）が検出された場合、LLM ベースのリゾルバが裁定し、根拠の弱いファクトを非活性化する。原論文のアブレーション研究では、矛盾解決が最大 2.45% の精度寄与を持つと報告されている。

**Stage IV — グラフ射影。** 4 層グラフが SQLite バックエンドのストアに具現化される。全ファクト・パッセージノードは OpenAI の埋め込み API で埋め込まれ、ベクトル類似度検索用にインデックスされる。

## 4. 主要な拡張

### 4.1 PPR における選択的ハブ抑制

**クリーンルーム実装中に発見した課題。** 論文の PPR アルゴリズムを均一なノード処理で再現したところ、高次数のスキーマノード（例: `(Person, is, Human)`）が PageRank のスコアを不均衡に吸収し、情報量の多いパッセージ・ファクトノードのスコアを希釈することを発見した。論文はこの問題に言及していない。

**解決策。** 次数閾値を超えるスキーマ層ノードに対してのみ、選択的なハブ抑制を適用する。総次数 $d > \theta$ を持つスキーマノードに対し、入力スコアを $\frac{1}{\log_2(d + 2)}$ で減衰させる。ファクトおよびパッセージノードは抑制されず、comparison 質問に重要なエンティティ固有の情報が保存される。

```
hubDamping(node) = 
  1/log₂(degree + 2)  node ∈ スキーマ層 かつ degree > θ の場合
  1.0                  その他
```

**パラメータ:** テレポート確率 α = 0.5、ハブ次数閾値 θ = 50、収束 ε = 10⁻⁶、最大反復回数 = 100。

**設計上の重要な決定（論文の範囲外）:** エンティティノードは PPR の遷移から*完全に除外*される。エンティティ共起部分グラフは過度に密であり、スコアが循環内に捕捉されてパッセージランキングの品質を低下させる。これはクリーンルーム開発中に経験的に発見されたもので、論文は PPR におけるエンティティノードの扱いを議論していない。エンティティノードは comparison 質問のシード初期化段階（§4.2）でのみ使用される。

**効果。** ハブ抑制により、スキーマノードが top-K パッセージを独占することが防止される。本コーパス（20,244 ノード、28,483 エッジ）において、スキーマノードの次数中央値は 214（グラフの 5%）であり、抑制なしの場合に大きなスコア吸収が生じることを確認した。

### 4.2 質問タイプ別の検索・プロンプト戦略

**クリーンルームベンチマークで発見した課題。** HotpotQA は本質的に異なる 2 種類の質問を含む: *bridge* 質問（80%、マルチホップ推論チェーンが必要）と *comparison* 質問（20%、複数エンティティの属性並列検索が必要）。論文は両方に単一パイプラインを使用する。我々のクリーンルームベースラインは bridge 49.5% vs. comparison 81.0% という顕著な非対称性を示し、均一な戦略が一方のタイプを犠牲にしていることを示唆した。

**解決策。** 正規表現ベースの comparison 検出器（HotpotQA で再現率 90%、精度 77%）を実装し、質問を専用パイプラインにルーティングする:

**comparison 質問の場合:**

1. **シード初期化でのエンティティ拡張。** ベクトル検索で初期シードファクトを特定した後、シードと head または tail エンティティを共有する追加ファクトを探索する。これにより、比較対象の両エンティティが PPR シードベクトルでカバーされる。拡張ファクトには 0.3 の減衰係数を適用し、最大 20 ファクトに制限してシード希釈を防止する。

2. **構造化比較プロンプト。** ステップバイステップのプロンプトで LLM に指示する: (a) 比較対象エンティティの特定、(b) 各エンティティの関連属性の検索、(c) 属性の直接比較、(d) 回答の決定。yes/no 質問では "yes" または "no" での回答を制約する。

**bridge 質問の場合:**

1. **エンティティ拡張なし。** bridge 質問は集中的な検索が有効であり、共有エンティティ経由の拡張は無関係なファクトからのノイズを導入する。

2. **チェーン追跡プロンプト。** マルチホッププロンプトで LLM に指示する: (a) 最初のエンティティの特定、(b) コンテキスト内の情報検索、(c) 推論チェーンの追跡、(d) 回答が質問の求める内容と一致するかの検証（中間エンティティではなく最終回答であること）。

**効果。** comparison 精度は 80.0%（v10）から 90.0%（v14）へ +10pt 改善した。bridge 精度は 76.0% から 82.0% へ改善した。comparison 用エンティティ拡張機構は v4 で導入され comparison 精度に +3.4pt 寄与し、プロンプト特化がさらに +6.6pt を加えた。

### 4.3 推論深度制御による回答生成

**実装分析を通じて発見した課題。** 現代の推論モデル（GPT-5、o1、o3、o4 系列）は推論深度（`reasoning_effort`: low/medium/high）と出力密度（`verbosity`: low/medium/high）の明示的な制御を提供する。これらの制御は原論文執筆時には利用できなかったものであり、API レベルで計算量と推論品質をトレードオフする根本的に新しい能力を表す。我々のクリーンルーム実装は当初、論文のアプローチに従い temperature のみを生成パラメータとして使用していた。API 動作の体系的分析を通じて、推論モデルが temperature を*完全に無視*し、推論トレースの変動によって非決定性が生じることを発見した。

**解決策。** 推論モデル対応の生成機構を以下のコンポーネントで実装した:

1. **モデル検出。** プレフィクス `gpt-5`、`o1`、`o3`、`o4` を持つモデルを推論モデルとして分類する。これらに対しては `reasoning_effort` と `verbosity` を送信し、`temperature` を省略する。

2. **effort/verbosity プロファイル。** 回答生成ステップでは `reasoning_effort=high`（深い推論チェーン）と `verbosity=low`（簡潔な最終回答）を組み合わせる。この組み合わせにより、出力トークンは約 13 倍増加（内部推論）する一方、抽出される回答は短くなる（中央値 18 文字 vs. 20 文字）。

3. **切り詰め回復。** 推論モデルは `max_completion_tokens` の予算を推論と出力の両方に消費する。`finish_reason=length` が返された場合（推論トレースが予算を使い切った場合）、`reasoning_effort=low` で 1 回リトライして完全な回答を得る。

| 構成 | 出力トークン | 回答長 | 精度 |
|------|------------|--------|------|
| effort パラメータなし（v10） | ~40 | ~20 文字 | 76.8% |
| `effort=high, verbosity=low`（v14） | ~526 | ~18 文字 | 83.6% |
| `effort=medium, verbosity=low` | ~300 | ~18 文字 | 83.2% |

**効果。** この単一の改善で **+6.8pt** を達成した — 全改良中で最大の精度向上である。誤答カテゴリ別の改善分布:

| 誤答カテゴリ | 改修前（v10） | 改修後（v14） | 変化 |
|-------------|-------------|-------------|------|
| 推論ミス（gold がコンテキスト内） | 66 | 47 | −19 |
| 検索ミス（gold がコンテキスト外） | 42 | 32 | −10 |
| yes/no 判定ミス | 8 | 3 | −5 |

注目すべきは、深い推論が見かけ上の検索ミスも 10 問削減したことである — モデルが、浅い推論では解決できなかった言い換えや間接的なエビデンスから正しい回答を合成できた。

**effort ラダー分析。** effort レベル間の制御実験を実施した:

| Effort | 精度 | 速度 | high との差 |
|--------|------|------|-----------|
| high | 83.6%（418/500） | 13.5s/q | — |
| medium | 83.2%（416/500） | 12.2s/q | −0.4pt（ノイズ範囲） |

medium は high の精度の 99.5% を 10% 低いレイテンシで達成し、問題レベルで 97.2% の一致（486/500 問が同一結果）を示した。本番環境では medium を使用し、最終評価のみ high を使用することが推奨される。

### 4.4 ドメイン語彙資源の統合

**先行研究からの着想。** 我々の以前の代替 GraphRAG アプローチに関する研究（シソーラス強化検索に関する Qiita 記事として文書化）で、ドメイン固有の専門用語と同義語関係が知識集約型 QA のエンティティ一致を大幅に改善できることを実証していた。原論文の MemGraphRAG はこれらの語彙資源を組み込んでおらず、すべての用語を不透明な埋め込み対象として扱っている。

**解決策。** クエリパイプラインに 2 つの語彙資源を統合した:

1. **専門用語辞書（Term Dictionary）。** 用語から正規形、カテゴリ、別名、信頼度スコアへのドメイン固有ルックアップテーブル。クエリ処理中に辞書が既知のエンティティを識別し、検索スコアリングに対してブースト係数を提供する。

2. **シソーラス拡張（Thesaurus Expansion）。** 同義語・上位語・下位語ネットワークにより、ベクトル検索前にクエリ用語を拡張する。拡張ポリシーは制限付き（クエリあたり最大同義語 3、上位語 2）であり、トピックドリフトを防止する。拡張語はクエリテキストに付加される: `"元のクエリ 同義語1 同義語2"`。

両資源は SQLite に格納され、再現性のためにエクスポート・インポートをサポートする。

### 4.5 堅牢な回答評価フレームワーク

**クリーンルームベンチマーク中に遭遇した課題。** HotpotQA の標準的な完全一致または単純な containment 指標は、偽陰性（表層形の違いによる正解の拒否）と偽陽性（部分文字列一致による誤答の受理）の両方を生じさせる。反復的なベンチマーク中に、評価ノイズが小幅な改善の信頼性ある測定を不可能にすることが判明した。論文は評価関数を詳細に記述していない。

**解決策。** 言語学的正規化に基づく 9 段階の階層的評価関数（`normalizedContains`）を開発した:

| ルール | 機構 | 例 |
|--------|------|-----|
| 1. 直接 containment | 双方向正規化部分文字列一致 | "Einstein" ⊂ "Albert Einstein" |
| 2. トークン重複（80%） | 複数語の gold に対し ≥80% トークン重複 | "Grammy Award" ≈ "Grammy Awards ceremony" |
| 3. 数値正規化 | 英語数詞→数字変換 | "twenty eight" → "28" |
| 4. 形態素ステミング | 接尾辞除去（ies/ves/s/ed/ing/ly） | "countries" → "country" |
| 5. ニックネーム展開 | 名前変形辞書（15 エントリ） | "Bill" → "William" |
| 6. 緩和トークン重複（60%） | 長い回答（≥3 トークン）に対する緩和閾値 | 言い換えられた複合語回答 |
| 7. 国名・地域別名 | 単語境界考慮の別名グループ | "USA" ≈ "United States" |
| 8. デモニム対応 | 国籍形容詞 ↔ 国名の相互一致 | "American" ↔ "United States" |
| 9. 人名ヒューリスティック | 姓 + 名プレフィクス一致 | "Bill Clinton" ≈ "Clinton" |

**重要な設計制約:** ルールは順序通りに適用され、先のルールが優先する。ルール 9（人名）は姓が一般名詞の場合に偽陽性を生じさせることが判明した（例: "the Atlantic **Ocean**" が "Pacific **Ocean**" に一致）。4 文字以上の姓を要求し、名のプレフィクスクロスチェックを追加して対処した。

**検証。** 独立に記述した評価関数で全 500 結果を再採点し、100% の一致を確認した。評価関数は v10.1 以降凍結され、後続のベンチマーク比較の方法論的一貫性を保証している。

### 4.6 LadybugDB グラフバックエンドとキャッシュアダプター

**スケーリング分析で発見した課題。** SQLite ベースのストレージアーキテクチャは大規模コーパスで 2 つのパフォーマンスボトルネックを示した: (a) `FileVectorIndex.search()` が毎回 ~500MB のバイナリベクトルデータに対して `readFileSync()` を実行（1 クエリあたり 3 名前空間検索 = ~1.5GB I/O）、(b) `SQLiteMemoryStore.load()` が毎回 113K 以上のファクトをディスクから再読込。さらに、SQL JOIN で表現されたグラフ操作はグラフ規模（全コーパスで 206K ノード、448K エッジ）に対して計算量が増大する。

**解決策。** **LadybugDB グラフバックエンド**（Cypher クエリ、HNSW ベクトル索引、全文検索をネイティブサポートするグラフデータベース）と、冗長な I/O を排除する 3 つの**インメモリキャッシュアダプター**を導入した:

1. **LadybugDB グラフストレージ。** グラフノードとエッジを LadybugDB のネイティブグラフ形式で格納し、SQL JOIN の代わりに Cypher ベースの走査を可能にする。マイグレーションで 206,458 ノードと 448,440 エッジを SQLite から LadybugDB に 35 分で移行した。

2. **CachedGraphProjection。** 任意の `IGraphProjection` 実装を Promise ベースの重複排除キャッシュでラップする。225,633 件の遷移を 1 回ロードし、以降の PPR 呼び出しにメモリから提供する。Cypher フルスキャン（LadybugDB）または SQL JOIN（SQLite）のボトルネックを排除する。

3. **CachedMemoryStore。** 任意の `IMemoryStore` をコーパス単位のスナップショットキャッシュでラップする。全メモリ（3,823 スキーマ、113,223 ファクト、9,987 パッセージ）を ~2s で 1 回ロードし、メモリから提供する。`save()` 時にキャッシュは自動無効化される。

4. **CachedFileVectorIndex。** 全ベクトルバッファ、マニフェスト、メタデータをメモリにプリロードする読取専用 `IVectorIndex` 実装。ブルートフォースのコサイン類似度計算を完全にインメモリで実行し、~1.5GB/query のディスク I/O を排除する。名前空間データ（passage + fact + schema で合計 ~1.2GB）はコーパスあたり 1 回のみロードされる。

3 つのアダプターはすべて標準ドメインインターフェース（`IGraphProjection`、`IMemoryStore`、`IVectorIndex`）を Decorator パターンで実装しており、任意のパイプライン構成にドロップイン置換可能である。

**アーキテクチャ:**

```
┌──────────────────────────────────────────────────────────────┐
│              v0.2.0 ハイブリッドアーキテクチャ                  │
│                                                              │
│  LadybugDB ──→ CachedGraphProjection ──→ PPR（インメモリ）    │
│  SQLite    ──→ CachedMemoryStore     ──→ コンテキスト構築     │
│  FileIndex ──→ CachedFileVectorIndex ──→ ベクトル検索         │
│                                                              │
│  全キャッシュは 1 回ロード、以降 O(1) で提供                    │
└──────────────────────────────────────────────────────────────┘
```

**パフォーマンス効果:**

| 指標 | キャッシュ前 | キャッシュ後 | 改善倍率 |
|------|------------|------------|---------|
| クエリレイテンシ | ~50s/query | 2.7s/query | **18.5×** |
| グラフ遷移ロード | 1 クエリあたり 42s | 初回 42s、以降 0ms | — |
| メモリスナップショットロード | 1 クエリあたり 2s | 初回 2s、以降 0ms | — |
| ベクトル I/O / クエリ | ~1.5GB ディスク読取 | 0（インメモリ） | — |
| 総ベンチマーク時間（500 問） | ~8 時間（推定） | 1,356s（23 分） | **~21×** |

**精度効果:** LadybugDB キャッシュ構成で **87.6%**（438/500）を達成し、SQLite ベースライン 83.6%（418/500）と比較して +4.0pt の改善。この差は実測ノイズ帯 ±3pt（§5.4）をわずかに超えており、ネイティブグラフバックエンドの PPR 計算による控えめだが実質的な改善を示唆する。Bridge 精度は 82.0% → 87.0%（+5.0pt）に改善; comparison 精度は 90.0% で維持。

## 7. 考察

### 7.1 推論深度が支配的要因である

本研究の最も重要な知見は、**推論深度制御**（+6.8pt）が全検索・グラフ改善の合計（v5 から v10 で +5.8pt）を上回ることである。LadybugDB バックエンド移行（v14 から v15 で +4.0pt）と合わせると、拡張による累計改善は +16.6pt に達する。これは、十分な再現率を持つ構造化 RAG システムにおいて、回答生成ステップ — 検索ではなく — が主要なボトルネックであることを示唆すると同時に、ストレージバックエンドの最適化がさらなる改善を提供できることも示している。

機構はトークン統計から明確である: `reasoning_effort=high` によりモデルは約 526 の出力トークン（大部分が内部推論）を生成するのに対し、effort 制御なしでは約 40 トークンであった。一方 `verbosity=low` が最終回答を簡潔に保つ。モデルは回答を確定する前に、効果的に多段階の内部審議を行っている。

これは RAG システム設計への含意を持つ: 再現率が十分であれば検索の精緻化への投資は収穫逓減をもたらし、計算予算を推論深度に振り向ける方が効果的である可能性が高い。

### 7.2 推論モデルにおける非決定性

同一入力・`temperature=0` で ±15 問（±3pt）のフリップ帯が恒常的に観測される。これは推論モデルに内在するものであり、内部推論トレースが呼び出しごとに変動することに起因する。この非決定性はベンチマーク精度の根本的な限界を課し、小幅な改善（<3pt）をノイズと統計的に区別不可能にする。

緩和策として self-consistency 投票を評価したが無効であった: 非決定性の起源が推論トレース（temperature 駆動サンプリングではない）にあるため、同一 effort レベルの複数サンプルは相関する。真に独立なサンプルには `reasoning_effort` の変更が必要であるが、それは品質分布を変えてしまう。

### 7.3 エンティティ拡張: 選択的適用

PPR シードにおけるエンティティベースのファクト拡張は comparison 質問に有益（comparison で +3.4pt）だが bridge 質問には有害（ノイズの導入）である。これは comparison 質問が*幅*（複数エンティティのカバー）を必要とし、bridge 質問が*深さ*（特定の推論チェーンの追跡）を必要とするという仮説を検証するものである。本質問タイプ検出器がこの 2 パターンを異なる初期化戦略にルーティングする。

### 7.4 クリーンルーム再現の価値

クリーンルーム手法は、論文のアーキテクチャを意味のある拡張が可能な深さで理解するために不可欠であった。我々の主要な革新 — ハブ抑制、エンティティノードの PPR からの除外、質問タイプ別シーディング — はいずれも、忠実な再現における予期しない動作のデバッグから直接生まれたものである。システムをゼロから構築しなければ、これらの暗黙的な設計判断は不可視のままであった。

クリーンルームベースライン（55.8%）と論文の結果（71.6%）の差もまた、未規定のエンジニアリング判断の重要性を浮き彫りにする: コーパス準備、埋め込みモデル選択、ハイパーパラメータ調整が集合的に約 16pt の変動を占めており、RAG システムの再現性にはアルゴリズム仕様以上のものが必要であることを示している。

### 7.5 制限事項

1. **コーパス特異性。** 本コーパス（100 学術論文）は HotpotQA の Wikipedia ベース知識源とは異なり、分布シフトの影響がありうる。
2. **評価の厳密性。** 本 9 段階評価は完全一致より寛容だが LLM-as-judge より厳密である。複雑な言い換えによる正解の拒否が残存する。
3. **モデル依存性。** 推論深度制御の改善は GPT-5/o 系モデル固有であり、他のモデルファミリーへの転移は保証されない。
4. **非活性ファクト状態。** ファクトの 99.2% が cascading activation バグにより `inactive` 状態のままである。これの修正と Stage III 矛盾解決の完全有効化は 1–3pt の未開拓改善余地を示す。

## 8. 結論

本稿では MemGraphRAG のクリーンルーム再実装と体系的拡張を報告し、HotpotQA で String Accuracy 87.6% を達成した — 原論文比 +16.0pt の改善である。我々のアプローチは、公開されたシステムの理解と改善のための方法論としてのクリーンルーム再現の価値を実証する。

論文のアルゴリズム記述のみから忠実な TypeScript 実装を構築し、MemGraphRAG のコアアーキテクチャ上の主張を検証した。クリーンルーム過程で論文に規定されていない暗黙的な設計判断を発見し、これらを 6 つの対象的拡張の出発点とした:

1. **4 層異種グラフ**と選択的ハブ抑制 — 論文のフラットなグラフトポロジーを拡張してスコア希釈に対処。
2. **質問タイプ別検索** — 論文にない差別化を導入し、comparison 質問にエンティティ拡張を、bridge 質問に集中検索を適用。
3. **推論深度制御** — 論文執筆後の LLM 能力を活用し、単一拡張として最大の精度向上（+6.8pt）を達成。
4. **ドメイン語彙統合** — 代替 GraphRAG アプローチに関する先行研究に着想を得たシソーラス・専門用語辞書の統合。
5. **厳密な評価方法論** — 反復的開発中の漸進的改善を信頼性をもって測定するために開発した 9 段階正規化一致関数。
6. **LadybugDB グラフバックエンドとキャッシュアダプター** — SQLite からネイティブグラフデータベースへの移行とインメモリキャッシュにより、+4.0pt の精度改善と 18.5× のクエリ高速化を達成。

最も重要な知見は、**推論深度制御単体（+6.8pt）が全検索・グラフ改善の合計（+5.8pt）を上回り**、ストレージバックエンドの最適化（+4.0pt）がさらなる改善を提供することである。これは、構造化 RAG システムにおける階層的最適化戦略 — まず深い推論、次にストレージアーキテクチャ — が最良の費用対効果を生むことを示唆する。**「十分な検索 + 深い推論 + 最適化されたストレージ」パラダイム**が「完璧な検索」の単独追求より効果的である可能性が高い。

クリーンルーム方法論自体も極めて有用であった: 第一原理からシステムを構築することで、原理的な拡張に必要な深いアーキテクチャ理解を得ると同時に、論文の表面的分析では不可視な最適化の機会を発見した。
